# Agreed differences between the Python and Rust behaviour

Every place where the Rust port deliberately does not do what the Python reference does.
A difference is added here in the pull request that introduces it, after the manager agrees
it. Anything not listed here is expected to behave exactly as the Python snapshot does.

| # | Where | Python | Rust | Why | Test |
| --- | --- | --- | --- | --- | --- |
| 1 | `sylvia_base::pyjson::loads` | Accepts integers of any size | Refuses an integer literal outside the signed or unsigned 64-bit range | `serde_json` would read it as a float and write it back with an exponent, silently changing hashed bytes. No shipped content has such a value. | `pyjson::tests::wide_integers_are_refused_not_rounded` |
| 2 | `sylvia_base::pyjson::loads` | Accepts the literals `NaN`, `Infinity`, `-Infinity` | Refuses them. In `sylvia_domain::ruleset_tests::parse_ruleset_tests`, where Python reads them and then reports "Scenario values must be finite JSON data.", the same `ruleset_tests_invalid` diagnostic says "Scenario file must contain unambiguous UTF-8 JSON." | A JSON value in Rust cannot hold them, and the Python encoders that matter already run with `allow_nan=False`. | Covered by `serde_json`'s parser; `domain_records_vectors::domain_records_match_python` (cases marked "row 2") |
| 3 | Strings everywhere | A `str` can hold a lone UTF-16 surrogate (from `"\ud800"` in JSON) | A `String` cannot; such input is refused at parsing | Rust strings are valid Unicode. | `sylvia-domain` `identity_vectors::strict_json_reads_like_python` (a lone `\ud800` value and a lone `\udc00` key, through both strict readers); `sylvia-base` `pyyaml_vectors::loading_matches_python_for_both_loaders` (a `"\uD800"` YAML escape, which `SafeLoader` turns into a lone surrogate and `sylvia_base::pyyaml` refuses with `UnicodeError`) |
| 4 | `sylvia_base::pyjson::loads` and every reader built on it | Accepts JSON nested up to roughly a thousand arrays or objects; deeper raises `RecursionError`, which the owner reports as an internal error | Refuses JSON nested 128 or more levels deep with an ordinary rejection (127 levels read). In `sylvia_domain::ruleset_tests::parse_ruleset_tests`, where Python reports "Scenario data exceeds the nesting or size limit.", the same diagnostic says "Scenario file must contain unambiguous UTF-8 JSON." | `serde_json`'s recursion limit, which counts down from 128 and fails on reaching zero. Python's limit is an accident of its interpreter stack, so there is no exact boundary to reproduce, and no shipped content comes near 127 levels. | `pyjson::tests::nesting_is_limited_to_127_levels`; `sylvia-domain` `identity_vectors::strict_json_reads_like_python` (200 levels); `domain_records_vectors::domain_records_match_python` (the case marked "row 4") |
| 5 | Integers in the engine: `sylvia_base::pystr::parse_int` and every integer computed from content, the model or the player (`sylvia-engine` dice and dice expressions so far; YAML `!!int` scalars in `sylvia_base::pyyaml`) | Integers are exact at any size: `int(text)` accepts any valid string of up to 4,300 digits, and sums, totals plus modifiers, margins and success counts never overflow | An integer outside the signed 64-bit range, from text or as a result, is refused with `ValueError("integer result exceeds the supported 64-bit range")` (`pystr::INT_RANGE_MESSAGE`); no clamped value is ever stored or computed with. `parse_int` reports it as `IntParseError::OutOfRange { negative }`. A caller that only compares the value with a limit (die sides and counts in the dice-expression readers) treats it as beyond every limit on its side, so it takes Python's branch and gives Python's message | A Rust JSON value cannot carry a wider integer (row 1), and no shipped content comes near the bound. Refusing keeps every stored or hashed value equal to Python's, where clamping would store a different number. | `number_vectors::int_matches_python` (every Python value beyond `i64`, including 19- and 20-digit edges); `dice_vectors::integer_edges_match_python_or_refuse` (modifiers, DCs, sides and thresholds of `i64::MAX` and `i64::MIN`, and 19- and 20-digit text through both dice-expression readers); `pyyaml_vectors::loading_matches_python_for_both_loaders` (`9223372036854775808`, `-9223372036854775809` and wider `!!int` scalars, through both loaders) |
| 6 | `sylvia_domain::content::schema` (every `jsonschema` caller) | For a schema-valued `additionalProperties`, visits the extra members in `set` order, which follows string hash randomisation, so the order of the resulting errors (and of `validate_content_shape`'s corrections) can change from one run to the next | Visits them in the order the members appear in the instance, one of the orders Python can produce | No implementation can match a randomised order on every run; instance order is deterministic and is what Python gives whenever the set happens to iterate in insertion order. `additionalProperties: false` sorts its extras, so its message is unaffected. | `content_vectors` and `schema_vectors`, generated with that one `set` pinned to instance order and the unpinned run compared |
| 7 | Provider usage counts: `sylvia_provider::pyobj::int_or_zero`, `PyValue::int_or_zero` and the usage readers in `sylvia_provider::chat` | `int(x or 0)` on a provider token count gives an exact integer of any size, and the cache-miss subtraction `prompt_tokens - cached` cannot overflow | Row 5's rule applied to provider values: a count outside the signed 64-bit range (an integer, a float or digit text), or a cache-miss result outside it, is refused with "Provider usage count is outside the supported integer range" (an accidental failure, so the stream ends with `ProviderConnectionError`); no clamped value is stored | The port's integer-overflow rule; no real provider reports counts near 2^63 | `pyobj::tests::counts_outside_64_bits_are_refused_not_clamped`, `chat_vectors::usage_sums_outside_64_bits_are_refused` |
| 8 | Request headers of `sylvia_provider::openai_compat` (OpenAI-compatible endpoints) | The OpenAI SDK and httpx also send `User-Agent: AsyncOpenAI/Python 2.53.0` (unless Sylvia sets one), `X-Stainless-Lang`, `X-Stainless-Package-Version`, `X-Stainless-OS`, `X-Stainless-Arch`, `X-Stainless-Runtime`, `X-Stainless-Runtime-Version`, `X-Stainless-Async`, `x-stainless-retry-count`, `x-stainless-read-timeout`, and httpx's `Accept-Encoding: gzip, deflate` and `Connection: keep-alive` | `User-Agent: SylviaGM/<version>` where Sylvia sets none, and none of the others. Every header Sylvia or the protocol sets goes out as Python sends it, in the same order: `Authorization`, `Accept`, `Content-Type`, `User-Agent` when Sylvia sets it, the connection's configured headers, `OpenAI-Organization` and `OpenAI-Project` from the environment, then the call's extra headers. `Host` and `Content-Length` are the HTTP client's | Agreed with the manager: do not imitate the Python SDK's identity or telemetry. The recorded sessions' `model_requests` headers show the Python set | `provider_vectors::header_assembly_matches_python`, `provider_vectors::streams_through_the_provider_match_python` (each request's headers) |
| 9 | `sylvia_domain::package_library` manifest file records, read by `sylvia_domain::package_archive::admit_package_archive` | A manifest file's `byte_count` of any size is accepted when the manifest is read (it is only checked to be a non-negative integer); admission refuses the archive later, when the member's real size differs, with `Package archive admission failed` (`archive_invalid`) and the diagnostic message `Indexed package file size does not match` | A `byte_count` outside the signed 64-bit range (2^63 up to 2^64 - 1, the widest row 1 lets through) is refused when the manifest is read, with the diagnostic message `Package file byte count is too large`, inside the same `Package archive admission failed` (`archive_invalid`) rejection. A wider literal is refused by row 1 as `Package manifest is not strict canonical JSON` | Byte counts are held as `i64`, under the integer-overflow rule (row 5); no real member can be that large (archives are limited to 64 MiB). Agreed with the manager | `archive_vectors::hostile_archives_fail_like_python` (cases "record file huge", 2^63, and "record file beyond 64 bits", 2^64) |
| 10 | `sylvia_base::pyyaml::safe_dump` (`config/_user_settings.py:55`, `builder/_ruleset_source.py:590`) | A `date` or `datetime` the value reaches twice is one object (an aliased timestamp, `a: &d 2026-01-01` and `b: *d`, loaded and written back), so `safe_dump` writes it once with an anchor and then as an alias: `a: &id001 2026-01-01`, `b: *id001` | Written in full each time: `a: 2026-01-01`, `b: 2026-01-01`. Lists, dicts and sets reached twice are anchored as in Python | A loaded date is a plain value in `sylvia_base::pyyaml::Value`, without object identity; giving dates identity would burden every reader for a hand-written alias of a timestamp. Both texts load back to equal values. | `sylvia-base` `pyyaml_vectors::a_date_reached_twice_is_written_in_full` (Python's anchored text for a date and a datetime, the port's text, and both loading back equal) |
| 11 | The WebUI host's `Server` response header (`sylvia_owner::webui::host`) | Sylvia sets none; aiohttp sends its default `Server: Python/3.12 aiohttp/3.14.3` | `Server: SylviaGM/<version>` on every response | Row 8's rule: do not imitate another library's identity. The frontend never reads it | `webui-guard` and `webui-remote` declare `server` in `ignore_keys`; every other header, status, reason and body is compared |

Open questions for the manager are raised in the pull request, not parked here.
