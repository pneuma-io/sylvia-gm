# Sylvia GM exact model-input examples

> **Status:** Public synthetic acceptance evidence, not product authority
>
> **Generated by:** `scripts/generate_model_input_audit_examples.py`

These files show the complete ordered input Sylvia supplied to a synthetic MiniMax M3 endpoint
through the production DM session, stateless MCP, provider adapter, and OpenAI-compatible wire paths.
They contain no private user campaign or credential data.

Generated captures stay local and are ignored by Git. Tests create fresh temporary examples, so a
clean checkout does not depend on someone's saved captures or an older copy of the GM instructions.

## Exactness boundary

The normative meaning of **what Sylvia would actually send** is defined in
[`alpha-architecture-contract.md` §9.2.1](../../architecture/alpha-architecture-contract.md#921-what-sylvia-would-actually-send).
These captures are the public synthetic evidence for that boundary; they do not redefine it.

Each `provider_request` contains the complete application-level `messages`, `tools`, and `options`.
Each correlated `provider_wire_request` contains the complete request passed to the provider client
after transport-specific conversion. Nothing model-visible is shortened, summarized, or replaced.
Only wall-clock timestamps and elapsed durations are omitted from these public copies. Ephemeral
campaign, inference, discovery, exchange, and tool-call identities are retained so the correlations
can be inspected exactly.

The synthetic endpoint deliberately returns no usage block. Accordingly, every response says
`"availability": "not_returned"` and uses `null` counts; Sylvia does not manufacture zeros. In a
real audited call, provider-returned input, output, cached, reasoning, and total token counts occupy
the same fields. The files are examples of the exact input tokens/content, not claims about how a
particular tokenizer would count them.

## Files and sequence

- [`current-dm-system-prompt.txt`](current-dm-system-prompt.txt) is the exact stable system message
  present in both examples, separated for Wan's prompt review.
- A current final Campaign File write includes an ordered response-block list. These deterministic
  examples supply narration blocks and release their text after the disposition succeeds. Older
  saved exchanges retain their supported recovery path; they do not define the current live format.
- [`ruleless-opening-and-history.json`](ruleless-opening-and-history.json) contains two complete GM
  responses across two inferences. In each response, the same GM returns its final prose and
  Campaign File disposition together. Sylvia holds the prose until the update result succeeds. The
  opening stores its scene; the ordinary reply explicitly records that it changed no durable truth.
  The second response follows a genuine user message with the opening TALK retained as history.
  There is no fabricated “Begin the story” user turn and no Ruleset mechanic.
- [`srd-rift-opening-combat.json`](srd-rift-opening-combat.json) contains the complete inference
  sequence across the semantic opening and the player declaring a strike, then ending the turn.
  If the creature wins initiative, the first strike starts combat and returns at a Player boundary;
  the example submits a separate quarterstaff choice there before ending the turn. Either order
  includes exactly one player attack. The opening first presents the Verdant Margin and Riftwolf as playable
  fiction without silently starting combat. The model selects encounter start; the engine performs
  parameterless begin/advance bookkeeping itself; Player boundaries wait for input; and a
  GM-controlled Riftwolf boundary asks the model to choose its action. The captured MCP calls and
  every intervening discovery show the surface changing after each commit. The same GM attaches its
  Campaign File disposition to each complete prose response, and Sylvia holds that prose until the
  disposition succeeds. Initiative is resolved by the real package mechanic, so regeneration may
  legitimately choose either actor first and produce a correspondingly longer or shorter sequence.
  No provider request exists solely to echo a deterministic lifecycle operation.

In the SRD file, `mcp_list_tools` records include `basis_revision`, `result_revision`, writer, open
TURNs, relevant Ruleset phase state, category, package identity, descriptions, and full schemas.
`provider_request.correlation.mcp_discovery_id` identifies the exact discovery used for that
inference. Additional `call_tool_revalidation` discoveries prove each chosen mechanic was checked
again against current authority before execution.

The synthetic MiniMax M3 transport does not add an assistant prefill. Its provider-client request
preserves the application's exact conversation roles and content; any future provider-only
transformation must remain visible as a separate audited request layer.
